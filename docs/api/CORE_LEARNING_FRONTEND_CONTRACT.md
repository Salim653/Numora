# Core Learning Student API — PROPOSED integration contract

**Status: PROPOSED.** The current generated OpenAPI contains only health endpoints. This document records the frontend's expected interface for Backend review; it is not an approved or implemented API. Once Backend controllers/DTOs land, regenerate OpenAPI, replace the provisional types in `apps/web/src/features/core-learning/types.ts`, and align the frontend with the generated contract.

All endpoints use `/api/v1`, Supabase access token Bearer authentication, UUID identifiers, camelCase JSON, ISO-8601 UTC timestamps, and `application/problem+json` errors. NestJS authorizes the current Student, each attempt, and level access. No endpoint accepts a client-computed score, elapsed time, XP, or unlock state.

| Operation                                                             | Expected request               | Minimum response                                                                                                                      |
| --------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /chapters`                                                       | —                              | `{ chapters: { id, title, order }[] }`                                                                                                |
| `GET /chapters/{chapterId}`                                           | —                              | `{ chapter, subchapters: { id, chapterId, title, order }[] }`                                                                         |
| `GET /subchapters/{subchapterId}`                                     | —                              | `{ subchapter, levels: { id, title, order, status, latestScore, bestScore }[] }`; status: `locked`, `open`, `inProgress`, `completed` |
| `GET /students/me/progress`                                           | —                              | `{ completedLevels, totalLevels, latestScore }`                                                                                       |
| `POST /assessments/drill/attempts`                                    | `{ levelId }`                  | Current/new attempt; repeated start for an active level returns the same in-progress attempt                                          |
| `GET /assessment-attempts/{attemptId}`                                | —                              | Attempt with `id`, `levelId`, `levelTitle`, `status`, `startedAt`, `isDemo`, and ordered `questions`                                  |
| `PATCH /assessment-attempts/{attemptId}/answers/{questionInstanceId}` | `{ optionId: string \| null }` | `{ questionInstanceId, selectedOptionId }`; `null` clears the answer                                                                  |
| `POST /assessment-attempts/{attemptId}/submit`                        | —                              | Persisted result; repeated submit returns the same result                                                                             |
| `GET /assessment-attempts/{attemptId}/result`                         | —                              | Persisted result with score, raw points, answer review, explanation, mastery, stars, and unlock effect                                |

Before submit, each question has `{ questionInstanceId, stem, options: { id, text }[], selectedOptionId }`. It must **not** include a correct option, answer key, or explanation. The demo package has 10 ordered `SINGLE_CHOICE` questions with A–D options; simple inline math uses `$...$`. The result adds `score`, `rawPoints`, `correctCount`, `questionCount`, `mastered`, `stars` (nullable while score-zero display is unresolved), `unlockedLevelId` (nullable), and `explanationState` (`available` or `expired`). Reviewed questions include `correctOptionId` and `explanation` only while explanation is available. Backend enforces the 90-day access limit without deleting the historic score.

Frontend saves each selection before allowing final submission. A failed save remains visible and retryable. Server owns the assessment lifecycle, finalization, 80% unlock rule, historical question/scoring context, and idempotency. The UI invalidates cached progress and level status after submit, then fetches the persisted result. Student onboarding and teacher monitoring have separate contracts and owners.

**Review needed before integration:** Backend confirms endpoint paths and response fields, defines authorization/error codes and answer-clear semantics, and publishes generated OpenAPI. QA verifies 7/10 stays locked, 8/10 unlocks, refresh resumes the same attempt, duplicate submit returns one result, and another Student cannot access the attempt.

## TryOut and Penilaian — PROPOSED

The web now exposes separate Practice & Drill, TryOut, and Penilaian areas. These additional endpoints are **proposals**, not implemented Backend contracts. TryOut is outside the first school trial and its official question count, duration, domain composition, and PGK scoring remain OPEN-05/OPEN-04. The frontend renders package values supplied by Backend; it does not choose defaults for those decisions.

| Operation                                                         | Expected request               | Minimum response                                                                                                                                                                                                    |
| ----------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /tryout/packages/current`                                    | —                              | `{ state: "unavailable" }` when no package exists; otherwise `{ id, title, releaseAt, state, eligible, attemptId, questionCount, durationSeconds }` with state `open`, `inProgress`, `waitingIrt`, or `resultReady` |
| `POST /tryout/attempts`                                           | `{ packageId }`                | Existing/new attempt for the current package; duplicate start does not consume another attempt                                                                                                                      |
| `GET /tryout/attempts/{attemptId}`                                | —                              | `{ id, packageId, packageTitle, status, deadlineAt, questions }`; answer key and explanations are absent                                                                                                            |
| `PATCH /tryout/attempts/{attemptId}/answers/{questionInstanceId}` | `{ optionId: string \| null }` | Acknowledged saved answer; `null` clears it                                                                                                                                                                         |
| `POST /tryout/attempts/{attemptId}/submit`                        | —                              | `{ state: "waitingIrt" }`; duplicate submit remains idempotent                                                                                                                                                      |
| `GET /tryout/attempts/{attemptId}/result`                         | —                              | Score and explanations **only after** IRT release; before that, `application/problem+json` with code `TRYOUT_RESULT_PENDING` and no score/key                                                                       |
| `GET /students/me/assessment-results?cursor={cursor}`             | —                              | `{ records: { attemptId, activity, title, submittedAt, resultState, score }[], nextCursor }`; `score` is `null` while a TryOut waits for IRT                                                                        |

Backend determines Student affiliation, weekly package selection at Monday 00:00 WIB, one attempt per package, any deadline, final score, and IRT release. The browser presents those states without locally granting eligibility or revealing a result early. Penilaian is the Student-facing result/history view, not a scoring engine. Historical Drill results stay available even when Drill explanation access expires after 90 days, subject to the final response contract.
